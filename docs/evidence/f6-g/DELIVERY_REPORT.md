## CLI and privacy contract

No argument means local capability metadata with DB/config/webroot gaps explicitly incomplete. There is no environment DB fallback or auto-load of application secret files. Optional private descriptors are separate:

`php bin/hosting-preflight.php --deployment-fd=3 --db-config-fd=4`

The caller opens regular owner-private0400/0600, single-link, bounded8KiB JSON files read-only. Never put secret values in argv/stdout/evidence. Original descriptor O_RDONLY flags are verified via Linux /proc/self/fdinfo; effective UID uses posix_geteuid when present or /proc/self/status otherwise. POSIX is not required for the preflight, but if the necessary descriptor/owner metadata is hidden, explicit private input fails closed without connecting. Basic no-FD local observations still work; no unsafe ownership fallback is used. This proc visibility requirement is a concrete CageFS/shared-hosting limitation to verify, not a claim that every cPanel plan supports the tool fully.

Deployment JSON permits only webroot, config_file, storage, session_path and optional integer web_php_version (PHP_VERSION_ID form). These are declared layout observations, not proof of actual server mapping or application environment binding. The webroot must be exactly this installation's public directory; storage cannot substitute an unrelated directory for native root/storage. Config contents are never read: only private regular-file owner/mode and location outside public are checked when a file is declared. Config.fromEnvironment also supports hosting-panel environment injection, so no local config file is globally required: absent file metadata remains UNKNOWN/UNVERIFIED and panel secret handling is not attested; a declared unsafe file still blocks. Absolute canonical Linux paths only, no links, hardlinks for private files, dot traversal or arbitrary stream wrappers. Storage/session accessibility is metadata only. Shared sticky files-session directories can be observed without inventing a universal0700 directory requirement; actual session-file isolation remains operationally unverified. open_basedir/access failures are sanitized and never repaired. No mkdir/chmod/write/delete/rename/session_start/cron or subprocess operation is performed by the tool.

DB JSON is exactly dsn, user, password, read_only=true. Only the explicit DB FD can reach a private connection factory. The initial connector accepts strict local mysql DSNs with host localhost/127.0.0.1/::1, optional port, dbname and charset=utf8mb4. Remote-host/socket/custom-init/TLS options are not implemented: a remote host remains UNKNOWN without a connection. Plans with a remote database need separate reviewed secure transport support/validation; no live host was contacted in this task. Nonpersistent PDO with multi-statements disabled and a two-second driver timeout option; no global wall-clock guarantee is claimed.

The native Core Database::connect is deliberately not reused because it executes SET. The only tool SQL is four literal metadata SELECTs: version/current session mode/zone/UTC offset/charset/schema selection, InnoDB support, DISKS plugin visibility and (only if active) one DISKS availability row. No application rows, DDL/DML/SET/GRANT/SHOW GRANTS, lock/transaction mutation or CREATE/DROP permission probe. Current metadata SQL mode/UTC observations do not prove that the native application account can initialize its own sessions. Query denial or hidden/empty metadata is UNKNOWN, not guessed. DISKS access is optional for general installation; the tool never installs a plugin. Account creation and server logging occur only in gated disposable test fixtures, never in the tool.

The JSON is fixed allowlisted strings and booleans/statuses, with no hostname/DSN/user/password/config values/private paths/raw exception or timestamp. Repeated equal observations produce byte-identical JSON. Raw private config, live data, actual F6-F encrypted archives/keys/restored contents and server logs are not evidence files and are never uploaded.
